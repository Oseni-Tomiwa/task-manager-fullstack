## Proxy trust and authentication rate limiting

**FAIL — release gate unresolved, high priority.** Source inspection confirms Express has no trust-proxy override, so its default is false. The login/register limiter uses the default IP key, a shared 10-attempt/15-minute budget and in-memory storage. It explicitly disables the `xForwardedForHeader` validation warning; this is existing code, not a change made here. The warning suppression is not evidence of correct identity extraction.

With default false, `req.ip` derives from the socket peer. Render documents Cloudflare/load-balancer ingress and proxy addresses being visible to the application. Vercel documents visitor forwarding headers for external rewrites. Together these establish a credible aggregation risk, but do not identify the exact deployed chain, trusted address ranges, header overwriting behavior after Render ingress, or two independent clients' effective limiter keys. No actual global/shared budget was measured, and no rate-limit boundary was exercised.

Direct Render API accessibility is confirmed. A non-browser caller can supply Origin and arbitrary forwarding headers; Origin is a browser CSRF defense, not proof that traffic came from Vercel. Therefore blindly trusting `x-real-ip`, `x-vercel-forwarded-for`, the leftmost X-Forwarded-For address, all proxies, or a guessed hop count could let a direct caller choose limiter identities. Vercel's documented sanitization does not authenticate headers arriving directly at Render. The direct and proxied paths also have different potential hop counts.

Relevant primary sources:

- [Express proxy trust semantics and hop-count warning](https://expressjs.com/en/guide/behind-proxies/)
- [Render ingress and client-IP guidance](https://render.com/articles/how-render-handles-ddos-attacks)
- [Vercel request-header semantics](https://vercel.com/docs/headers/request-headers)
- [Vercel visitor forwarding and origin restriction](https://vercel.com/docs/routing/rewrites#identifying-the-visitor-at-your-origin)

**Smallest next diagnostic, proposed only:** separately approve a temporary, secret-gated observer on the existing health route, with a short TTL, a fixed eight-request cap and predefined probe tags. Use two controlled networks, direct/proxied paths, and one baseline/one synthetic spoofed-header request per path/network: eight requests total, none to login/register. Observe the socket peer, bounded forwarding chain and candidate key internally; output only chain lengths and equality/matches-expected booleans for the controlled cases. Never log raw IPs, full headers, secret gate values, cookies, tokens or arbitrary inputs; leave health responses unchanged and expose no public debug endpoint. Authenticate the probe gate independently of client-supplied Origin. The second controlled network and expected identities must be provided privately by the owner. Instrument before any candidate trust change.

After evidence: prefer the smallest tested trust/extraction policy that distinguishes the controlled clients and resists spoofing on both paths, using provider-supported trusted boundaries. If the chain cannot be authenticated reliably, consider a separately reviewed Vercel-to-origin secret gate/header overwrite and a narrowly defined client-key policy, preserving any explicitly needed direct health access. Vercel documents an environment-backed origin-secret approach; do not hardcode a secret in public Git. Such a gate changes direct API behavior and requires separate approval, not an automatic fix. Do not raise the limit, disable more validation, introduce a distributed store or change authentication just to hide the issue. Remove the observer after validation.

## API caching

**PASS — static configuration and sampled unauthenticated live responses. NOT VERIFIED — personalized cross-account production responses.**

`client/vercel.json` forwards `/api/:path*` to the exact Render `/api/:path*` endpoint before the SPA fallback; the fallback excludes `/api` and descendants. It preserves reviewed static headers and sets API Cache-Control, CDN-Cache-Control and Vercel-CDN-Cache-Control to `no-store`, plus `x-vercel-enable-rewrite-caching: 0`. Fresh static assertions checked the destination, ordering, exclusion and cache opt-out. Browser fetches also use `cache: "no-store"` and same-origin credentials.

Every sampled Vercel API response, including 401, 403, 404 and 204, had Cache-Control and CDN-Cache-Control `no-store` and X-Vercel-Cache `MISS`. Sampled Render auth/task/health responses had Cache-Control `no-store`; its public unknown-route 404 had no explicit cache directive, but contains no personalized data. Vercel's API rule supplied no-store on that proxied 404. Some platform CDN headers may be consumed rather than returned to the client. A cache MISS alone does not prove permanent non-caching.

[Vercel currently documents cache-control-aware external rewrite caching for newer projects and the explicit `0` opt-out](https://vercel.com/docs/routing/rewrites#disabling-caching-for-rewrites-to-external-origins). Configuration matches that guidance; no genuine cache-configuration defect was identified, and none was changed. No authenticated 200/Set-Cookie response or two-account cache-isolation experiment was performed. Static SPA HTML cache hits with revalidation are expected and are not personalized API cache leaks.
